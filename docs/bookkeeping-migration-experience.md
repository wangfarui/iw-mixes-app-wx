# 原生微信小程序迁移与记账模块优化经验

本文档沉淀 `iw-mixes-app-wx` 记账模块从 uni-app 迁移到原生微信小程序期间形成的经验。后续在其他对话中优化餐饮、积分任务、基础功能等模块时，可以把本文作为上下文，用户只需要说明“哪个页面 + 具体细节”，AI 即可按本文约定继续设计、实现、自验。

## 适用范围

- 目标项目：`iw-mixes-app-wx`
- 参照项目：`iw-mixes-app`
- 后端接口来源：`iw-mixes-server`
- 当前经验来源：账单、快捷记账、表单记账、记账记录、支出统计、收入统计、年度统计、会员订阅等记账相关页面的原生小程序改造

## 核心原则

1. `iw-mixes-app-wx` 必须保持原生微信小程序源码，不引入 Vue、uni-app、`uni.*`、`uni_modules` 或 Vue 模板语法。
2. 业务接口、字段含义、枚举取值优先从旧 uni-app 页面、`api` 封装和后端 Controller/DTO/VO 确认，不凭感觉发明。
3. 后端服务代码默认不改；小程序通过现有接口、请求参数、前端适配和样式重构完成迁移。
4. UI 目标优先贴近旧 uni-app 的真实使用体验。旧 UI 明显不理想时，可以在保持交互一致的前提下做现代化优化。
5. WeUI 只作为基础能力优先选项。若 WeUI 组件导致布局、间距、弹框、按钮、输入框等无法贴近目标效果，应手写最小业务组件。
6. 每次改动要自验：静态检查、路由检查、微信开发者工具编译，以及必要时用自动化/截图验证页面状态。

## 后续对话使用方式

后续可以直接这样描述需求：

```text
参考 iw-mixes-app-wx/docs/bookkeeping-migration-experience.md，
优化 pagesEat/eat/meal/index 页面。
细节点：
1. 顶部筛选区改成旧 uni-app 的样式。
2. 列表金额/长数字不能撑破布局。
3. 弹窗按钮文本需要居中。
```

AI 应按以下顺序处理：

1. 读取根目录 `AGENTS.md` 和目标项目 `iw-mixes-app-wx/AGENTS.md`。
2. 读取本文档。
3. 定位目标页面在 `iw-mixes-app-wx` 的 WXML/JS/WXSS/JSON。
4. 必要时读取 `iw-mixes-app` 对应旧页面作为 UI 和交互参照。
5. 必要时读取 `iw-mixes-server` 对应接口确认字段和枚举。
6. 按本文通用 UI 规范主动检查目标页面，发现按钮过宽、日期/输入框比例不合理、行间距拥挤等问题时一并修复。
7. 默认可以打开微信开发者工具调试 UI；除非用户明确要求不打开，否则不需要额外确认。
8. 只改 `iw-mixes-app-wx`，除非用户明确要求跨端或后端修改。
9. 实现后运行验证并说明结果。

## 推荐实施流程

1. 确认页面路径和入口：检查 `app.json`、分包路径、菜单跳转、tabBar。
2. 对照旧 uni-app 页面：看页面结构、弹窗方式、按钮位置、列表密度、关键工作流。
3. 对照接口数据：检查 `api/*.js`、请求封装、后端 Controller、DTO/VO、枚举。
4. 确定交互还原策略：WeUI 可用则用；不适配则手写原生 WXML/WXSS。
5. 小步改造：先结构和数据，再样式，再交互，再异常状态。
6. 自验自改：至少执行 `npm run check:routes`，涉及 UI 的页面默认使用微信开发者工具 `preview` 或自动化能力检查页面状态。
7. 最终说明：列出改动文件、验证命令、未覆盖风险。

## 已形成的通用 UI 经验

### 布局

- 移动端工具型页面应紧凑、稳定、可扫读，不做营销式大卡片堆叠。
- 固定格式控件要给稳定尺寸，例如键盘格、tab、筛选栏、统计卡、图表 canvas。
- 页面底部操作区要考虑安全区，不要出现无意义空白。
- 重要金额、数量、按钮文字不得换行，必要时设置 `white-space: nowrap`。
- 长数字、长备注、长 `recordSource` 要允许断行，常用组合：

```css
word-break: break-all;
overflow-wrap: anywhere;
```

### 表单与按钮

- 按钮文字必须水平/垂直居中，原生 `button` 样式不适配时可改用 `view` 手写按钮。
- 输入框、日期选择、按钮同一行时，默认让输入框/日期框使用弹性宽度，按钮保持只容纳文字的紧凑宽度，不要把重置、筛选、确认等短按钮做成等分大按钮。
- 横向筛选或日期行里的“重置”“筛选”等短按钮，如果原生 `button` 默认样式导致过高、过宽或文本不居中，直接换成紧凑的 `view` 按钮；推荐 `height: 56rpx`、`flex: 0 0 auto`、`padding: 0 20rpx-24rpx`、`white-space: nowrap`，只按文字占宽。
- 只有业务上需要固定比例时才设置比例，如任务页底部输入区曾采用 `5:3:2`；否则优先使用日期/输入框 `flex: 1`，按钮 `flex: 0 0 auto` 或明确的小宽度。
- 弹窗里的操作按钮如果被 WeUI 默认样式影响，应手写弹窗布局。
- 需要阻止遮罩点击冒泡时，弹窗按钮优先使用 `catchtap`。

### 弹窗

- 快捷记账中的“标签”“更多”应使用底部弹窗，不在备注区下方展开。
- 弹窗高度应随内容数量自适应，同时设置最大高度和滚动，避免内容过多撑出屏幕。
- 附件上传弹框按业务要求可以横向占满或纵向排列，不要被默认按钮宽度挤偏。
- 编辑弹窗应先用当前列表数据立即打开，再异步拉详情刷新，避免接口慢时表现为“点击没反应”。

### 列表

- 账单/记录列表中，标题、分类、时间之间保留少量间距即可，不要出现大块空白。
- 支出金额颜色统一，收入金额颜色统一，金额列靠右且不换行。
- 记录来源全数字且很长时要断行，不能遮挡右侧金额或操作按钮。
- 详情卡片和列表项不要嵌套过多卡片；必要时使用分隔线和紧凑间距。

### 图表

- 原生小程序内统计图优先用 canvas 手写轻量图表，避免为单页引入过重依赖。
- 空数据文案只保留一处，避免 canvas 和外层 DOM 同时显示“暂无数据”。
- 饼图图例应支持点击置灰并从图中移除该项。
- 图例百分比应靠右，便于扫读。
- 年度趋势适合曲线图，净收入为负的月份用红色点/红色月份提示。
- 柱状图适合月度每日消费、年度每月支出/收入趋势。

## 记账模块关键经验

### 快捷记账

- 是核心高频功能，应优先贴近旧 uni-app UI。
- 支出/收入切换、分类宫格、备注、金额展示、数字键盘布局要保持稳定。
- “标签”“更多”必须是弹窗交互。
- 备注输入最大长度限制为 64。
- 附件、货币、不计入统计、共享家人等非主流程信息应放在“更多”弹窗。
- 分类设置的上移/下移需要匹配后端更新接口真实字段，不能只前端重排。

### 记账记录

- 顶部分类和筛选区应贴近旧版，避免突兀的大按钮。
- 日期选择框和重置/筛选按钮要保持紧凑，重置按钮只需容纳文字。
- 汇总区支出/收入金额不换行。
- 筛选弹窗按钮文本居中，“确定”文案按需求改为“确认”。

### 账单与首页今日记录

- `recordType` 与标题、时间之间的上下间距要小而明确。
- 长数字 `recordSource` 必须断行。
- 列表右侧金额不能被长文本遮挡。

### 支出统计

- 总支出、笔数、忽略账单应在同一张顶部卡内形成清晰左右结构。
- 本月支出占比、支出标签占比使用饼图 + 图例 + 进度条组合。
- 支出标签支持按次数/金额切换。
- 月度每日消费使用柱状图。
- 饼图图例点击后置灰，图中移除该项。

### 收入统计

- 本月收入趋势改为柱状图，可复用支出统计的柱状图逻辑。
- 收入金额颜色和支出区分，排行金额不换行。

### 年度统计

- 年份选择不要显示突兀的向下箭头。
- 年度趋势分析使用曲线图展示支出、收入、净收入。
- 净收入为负的月份需要一眼可见，曲线点和月份文字可用红色强调。
- 记账习惯分析：
  - 记账天数显示单位“天”。
  - 连续记账最长显示单位“天”。
  - 记账次数最多月份下方显示次数。

### 会员订阅

- 列表页贴近旧 uni-app：搜索框、服务类型/到期类型/排序筛选、三张汇总卡、列表项、右侧状态和删除按钮、悬浮新增。
- 新增订阅表单沿用当前实现，不强行重构。
- 编辑订阅点击后应立即弹出编辑框，再异步获取详情刷新。
- 动作面板按钮使用 `catchtap`，避免遮罩冒泡导致无响应。

## 验证清单

常用命令：

```bash
cd iw-mixes-app-wx
npm run check:routes
node --check <target-page>.js
```

推荐额外验证：

```bash
/Applications/wechatwebdevtools.app/Contents/MacOS/cli preview \
  --project /Users/wangfarui/workspaces/wfr/iw-mixes_ai/iw-mixes-app-wx \
  --compile-condition '{"pathName":"pagesBookkeeping/bookkeeping/<page>"}'
```

复杂 UI 建议使用微信开发者工具自动化能力检查：

- 页面能打开。
- 关键弹窗能出现。
- `showForm`、`showActions` 等关键状态符合预期。
- canvas 图表非空且空数据文案不重复。
- 长文本、长数字不会遮挡金额或按钮。
- 日期筛选、搜索、表单操作等横向工具栏中，按钮应保持紧凑宽度，日期/输入框应使用弹性宽度。
- 筛选行、汇总行、统计卡之间应留出少量清晰间距，不能显得拥挤。

## 后续模块迁移提醒

### 餐饮模块

- 先看 `pagesEat/eat/eat-common.wxss`、`eat-helper.js` 是否已有共享模式。
- 餐食、菜品、冰箱、菜谱页要重点检查列表密度、表单弹窗、图片/附件、长名称换行。
- 若旧 uni-app 使用特殊交互，优先还原业务流程，再优化视觉。

### 积分任务模块

- 先看 `pagesPoints/points/points-common.wxss` 和 `pages/task/index.*`。
- 任务录入区、积分明细、计划新增/编辑页要重点检查底部操作区、安全区、按钮居中、日期选择比例。
- 积分记录等带日期筛选的页面，日期框应使用弹性宽度，重置等短按钮应尽量紧凑；日期筛选行与本月新增、扣减等统计行之间要留少量空隙。
- 积分统计若有图表需求，优先复用记账统计中的 canvas 经验。

### 基础功能模块

- 字典、账号、家庭组、我的页面偏管理型，应保持清晰表单、紧凑列表、明确空状态。
- 字典和枚举相关页面不能凭前端文案猜字段，应优先查后端和旧页面。
- 登录失效统一走 `api/request.js` 和 `utils/auth.js` 既有逻辑。
