# 衣柜设置实施清单与接口补充

日期：2026-10-22。状态：已按用户后续授权实施；当前结果及未覆盖项见 ../../acceptance/wardrobe-settings-20261022-dev/README.md。以下清单保留设计时计划，实际测试环境已按用户要求改为现有本地数据库与 Redis。用户确认以[主方案](README.md)第1节为准；数据库模型以[技术契约](investigation-20261022/TECHNICAL.md)为基础，本文补齐执行细节。本文所有新增接口、字段、状态与脚本名均为**计划新增**，不是现网已提供的能力。

## 2. 模块与数据约束

iw-auth管理字典来源、作用域、权限与一次性初始化；iw-web定义WardrobeDictionaryAccess及无状态值对象；iw-wardrobe核验真实业务权限、构造业务快照和统计。业务授权通过后才能取得所属人候选，禁止auth反向依赖wardrobe。

base_dict保留旧ID、scope_type、family_group_id、dict_code、previous_id和revision；衣柜增加独立稳定品类谱系、搭配归类、二进制名称生成键及唯一约束，不扩展记账active_name_key的类型集合。其他类型的衣柜名称键为NULL，不对记账或其他字典新增唯一约束。

- 品类首版lineage_id=自身ID，后继继承；款式的lineage_id指品类首版，parent_id指品类当前版本。插入/补谱系在同事务中完成，提交前断言不能为NULL或0。
- 品类名称唯一；款式名称按稳定品类谱系唯一。停用项占用名称，逻辑删除版本不占用。品类名称+搭配归类用于候选合并和统计区分，谱系ID不用于跨范围合并数据库行。
- 遗留品类码用于迁移时确认1–11的搭配含义；超范围或语义不明时停止，不用字典ID、parent_id或名称猜归类。生产P15/P16的唯一来源检查不能替代该范围断言。
- 新自定义来源不再要求分配旧业务编码。无法安全表达的旧category/item_style/CSV值写0/空串作为非权威占位，不能把新来源ID截断写入TINYINT/SMALLINT。所有新读、过滤、算法和统计先切至快照/搭配归类；任何仍以旧码作为新业务权威的消费点均阻止切换。
- 正式DDL须比对已有同名列/索引的**定义**，不是只判断“存在”。DDL隐式提交，不能声称一个ROLLBACK可以撤销整份结构迁移。

标量快照和多标签快照列详见技术契约。多标签表主键选BIGINT UNSIGNED，business_id/source_id沿用业务INT UNSIGNED；business_type用受校验的ITEM/OUTFIT/WEAR_RECORD值，ordinal从1开始。多态业务ID不能用一条伪外键宣称约束完成；写入由服务事务保证，离线校验断言无孤儿。衣物/搭配/记录的逻辑删除不物理清除历史标签，读取须关联已鉴权的业务主表，不能直接按source_id跨用户查标签。

## 3. 初始化与作用域身份

业务列表GET保持只读。已有六个生产个人来源集合保持原ID/父子结构，只建立衣柜作用域状态；不按测试库缺源现象补个人模板。已确认的家庭五类模板初始化仍需重建个人以外的独立父子来源。

| 时机 | 实施入口与规则 |
|---|---|
| 新用户 | 在当前用户注册字典初始化链路接入衣柜初始化；通用copyMissingVisibleDictData排除五类，衣柜只由专用初始化维护，不双重复制 |
| 新家庭 | 在AuthFamilyGroupServiceImpl.add现有记账初始化调用附近，同事务增加衣柜初始化；成功建立成员/归属后复制模板，不依赖成员先打开管理页 |
| 已有用户/家庭 | 受控迁移补作用域状态与家庭默认树；已有个人行不覆盖、不因状态缺失就认定无历史 |
| 管理上下文状态异常缺失 | GET返回DICTIONARY_NOT_READY。管理者可自动调用下述幂等初始化POST，再重新GET；不是将异常空列表当作删空 |
| 普通成员/儿童遇到家庭缺状态 | 返回未就绪与重试提示，不用只读账号调用管理初始化；正常创建/迁移链路应确保不会依赖家长首次访问才有默认项 |
| 用户已删空 | 状态仍存在，返回真实空列表，初始化POST不得补回模板 |

计划 `POST /auth-service/wardrobe/dictionaries/initialize`：请求`{scope:PERSONAL|FAMILY,expectedFamilyGroupId?}`；个人只允许本人，家庭只允许当前群主/家长且预期家庭一致；不接受任意ownerUserId、字典内容或模板版本。返回`{initialized,scopeVersion,familyGroupId}`，已初始化返回现状态，不增scopeVersion、不补项。缺状态但已有行时必须先验证完整性再建立状态，不得盲目重拷。代录孩子的候选GET不变成可初始化/管理孩子个人字典的旁路。

锁顺序应与现有家庭角色/归属修改链路对齐：有效家庭/成员/用户身份 → 按稳定键排序的作用域状态 → 按ID排序的来源 → 业务及其明细/标签。不能只在字典模块内部规定顺序而忽略AuthFamilyGroupServiceImpl的锁。事务中重新核验角色、有效家庭及业务所属人；移交、退组、改角色与保存相撞时拒绝过期上下文，不写到新家庭或其他所属人。

## 4. 统一选项与管理请求

所有计划对前端路径为`/auth-service/wardrobe/**`；Controller内部为`/wardrobe/**`。管理方法清单见技术契约第5.1节，补充约束如下：

- FAMILY管理读写均携带expectedFamilyGroupId；所有管理写入携带scopeVersion，单行操作另携带revision。删除通过query参数携带，避免依赖DELETE请求体。
- 名称只去首尾约定Unicode空白，按码点验证1–32，不折叠内部空格或大小写；碰撞返回名称已存在，输入保留。无名称变化不创建后继、不增加scopeVersion。
- 排序提交当前type/父谱系内全部未删除行（包括停用行），集合相同才允许更新；列表按启用/停用展示不改变完整排序集合。
- 从个人添加家庭项同时带个人与家庭scopeVersion以及sourceIds；只复制当前本人未删除且启用项。名称已存在（含停用）跳过；款式父项停用或搭配归类冲突时拒绝对应分支，不复活或改写目标项。先计算完整结果，同事务执行；返回created、skipped及原因、父子映射和最新scopeVersion。

计划`GET /auth-service/wardrobe/options`：businessType=ITEM/OUTFIT/WEAR_RECORD，创建可带ownerUserId，编辑带businessId；ITEM先用现有衣物访问服务验证创建/编辑/代录权限；OUTFIT/WEAR_RECORD保持现有所属人规则，不因传ownerUserId就增加代创建权限。返回内容示意：

```json
{
  "ownerUserId": 6,
  "familyGroupId": 10,
  "contextToken": "opaque-context",
  "personalScopeVersion": "opaque-personal-version",
  "familyScopeVersion": "opaque-family-version",
  "categories": [
    {"key":"category-group","name":"上装","matchKind":1,"preferredSourceId":101,
     "sources":[{"id":101,"scope":"PERSONAL"},{"id":201,"scope":"FAMILY"}],
     "itemStyles":[{"key":"style-group","name":"衬衫","sourceId":202,"categorySourceId":201}]}
  ],
  "colors": [], "scenes": [], "styleTags": []
}
```

示例数字仅说明结构，非生产ID。顶层styleTags表示穿搭风格，categories[].itemStyles表示衣物款式；DTO与前端保持这些名称，避免混用。候选key只用于合并展示；真正保存的是sourceId及其真实父来源。空数组不回退内置默认项。

contextToken绑定业务类型/ID或创建上下文、实际所属人、预期家庭与作用域版本；不是授权凭据，保存仍鉴权。候选失效返回刷新提示，不静默追随改名后继或换成同名家庭项。未修改任何字典字段的编辑不要求重新选择失效来源。

## 5. 衣物新增、局部更新与返回

计划修改现有`POST /auth-service/wardrobe/item/add`及`/batchAdd`：以dictionarySelection表达来源，代录ownerUserId与现有访问服务保持一致；批量逐件具有真实所属人上下文并在事务中统一校验。

```json
{
  "ownerUserId": 6,
  "itemName": "示例衣物",
  "dictionaryContext": {"contextToken":"opaque-context"},
  "dictionarySelection": {
    "categoryId":201,"itemStyleId":202,"colorId":null,"sceneIds":[],"styleIds":[]
  }
}
```

品类必填且来源ID大于0；款式可空，但非空必须属于选定品类真实来源。多选ID先去重并保留首次顺序；来源属于允许类型/所属人或有效家庭且启用，款式父项也须启用。客户端传name或历史来源例外标记一律不作为保存依据。

现有`PUT /auth-service/wardrobe/item/update`改为显式patch：

```json
{
  "id":32,
  "price":100,
  "dictionaryContext":{"contextToken":"opaque-context"},
  "dictionaryChanges":{"colorId":null,"sceneIds":[501,502]}
}
```

- dictionaryChanges缺省或空对象：从事务内读取的当前业务快照保留全部字典字段。
- 字段缺省：保留；colorId/itemStyleId=null：清空；sceneIds/styleIds=[]：清空；categoryId=null：拒绝，不将缺省字段解读为null。
- 只新选场景时，只刷新场景对应快照；不能顺带把品类/款式刷新成字典当前名称。多选整个字段被明确替换时，按此次来源重新生成该字段列表。
- 换品类时，必须同时给出匹配的新款式或itemStyleId=null；不可保留跨品类款式。显式提交原来源ID也视为重新选择，名称按此时合法来源生成。
- 同时移交所属人并修改字典项时，先验证旧对象维护权及目标所属人可管理性，新选择按目标所属人；未改字段保留旧快照。UPDATE继续携带原所属人条件，检测并发转交。
- 使用能区分JSON缺省和显式null的请求模型；普通nullable Java字段和无差别BeanUtil.copyProperties不能实现该契约。

列表/详情/批量创建回读返回dictionarySnapshot，其中每个字段含sourceId、nameSnapshot，品类另有matchKind，款式保留品类路径；多选为有序数组。设置历史项不可选标记时批量查询来源状态，不以状态查询失败覆盖名称。编辑页回显来自snapshot，不在onShow或候选刷新时改写已存来源。

## 6. 搭配与穿着记录的明细保留

现有add/update/copy/markWorn入口均保留原业务访问控制与衣物可用性检查，新增“保留旧明细”和“新加入衣物”的显式区分。不得继续使用完整itemIds列表删除重建全部明细。

编辑请求示意（计划字段）：

```json
{
  "id":1,
  "remark":"只修改备注的示例",
  "itemSetVersion":"opaque-current-detail-set",
  "items":[{"detailId":1},{"itemId":40}],
  "dictionaryChanges":{"sceneIds":[]}
}
```

items缺省表示保留全部明细；显式items按最终顺序提交，detailId必须属于此主记录且当前未删除，保留其来源/名称快照；itemId表示新加入，重新验证衣物访问/状态后复制衣物已保存快照，不按当前字典重新命名。同一条不能同时有detailId和itemId，拒绝重复ID、跨主表明细及空集合。删除的明细逻辑删除，保留项只改排序，不换ID。对明细集合进行修改时校验itemSetVersion，按事务内实际集合/顺序生成并比较，防止旧编辑器覆盖其他会话新加项。该版本不复用字典scopeVersion。

穿着记录涉及outfitId时：保持同一搭配且未明确更换明细，就保留穿着记录原明细，不因搭配后来编辑而刷新；明确重新选择搭配时，按当时可用的搭配明细快照重建目标集合。换到直接选衣物/换搭配的模式必须显式提交，不能仅用一个缺省outfitId推断。主记录的场景/风格同样使用显式dictionaryChanges。

| 动作 | 快照来源 | 可用性边界 |
|---|---|---|
| 新衣物加入新/旧搭配 | 衣物已保存快照 | 按现有可见衣物及状态核验 |
| 搭配/记录只改日期、天气、备注 | 数据库中的原主表字段与保留明细 | 不要求把历史失效字典重新选择；不借编辑新增不可用衣物 |
| 搭配copy | 有权复制的原搭配主表与明细 | 保留现有已删/转交衣物检查，不能为保留名称扩大物品权限 |
| 记录copy | 有权复制的原记录主表与明细 | 不能经add重新读取当前outfit或item；物品可用性仍按既有规则处理 |
| 从搭配新建穿着记录 | 已鉴权搭配的明细快照 | 保留已删/转交确认及仅使用可用衣物的既有流程 |
| 计划markRecordWorn | 原记录与明细 | 只改变状态并沿用原计数/幂等逻辑，不刷新字典名称 |

原记录sourceId即使已删除或不再属于当前家庭，也可在服务端可信复制中保留；不得由客户端把任意已删/他人来源声明为“历史复制”。复制不写原对象，不复活旧字典。新对象自身来源与名称一起复制，迁移解析的来源也保留其基线标记。

## 7. 历史筛选、统计与AI

新增选项只从当前可用字典取得；历史筛选只从有权查看的业务快照产生，两者不共用缓存。计划`GET /auth-service/wardrobe/filters?businessType=...`，沿用现有仅本人/家庭/指定所属人的可见性判定，返回品类、款式路径、颜色、场景、风格的历史名称候选与filterKey。后续page接口接受对应filterKey；key编码类型/名称/父路径/搭配归类，不能把sourceId当作名称桶或绕过权限的凭据。服务端按相同可见集合过滤，不先从全库生成候选再过滤结果。

快照名称规范化与新增名称一致；历史基线保持用户已确认文字，不另做大小写、同义词或英文翻译合并。款式按品类路径且品类搭配归类区分；标签统计对同一业务ID/类型/名称去重，再计对象数。衣物转交后历史搭配仍显示原快照，但不由历史筛选扩大该衣物现在的维护/可穿权限。

自动搭配规则改读category_match_kind_snapshot；新自定义“外套”可按上装规则处理，不使用新字典ID或旧category占位0分桶。AI识别使用获准所属人的当前候选和上下文输出sourceId，保存时再次鉴权和校验；AI返回旧码、任意名称、过期来源或不配套父子项时不自动落库。图片优化任务仅更新图片，轮询状态不能刷新字典快照，也不引入新的模型选择或供应商协议。

## 8. 统一错误与请求版本

以下为计划业务错误标识，落地时按项目响应包装实现；不擅自把业务冲突变成401并清空登录状态。

| 标识 | UI与服务端要求 |
|---|---|
| DICTIONARY_CONTEXT_CHANGED | 所属人/家庭/版本变化，保留草稿并提示刷新候选，不自动提交到新范围 |
| DICTIONARY_SOURCE_UNAVAILABLE | 来源被停用/删除/改名或父项失效；只要求替换字段重新选择 |
| DICTIONARY_NAME_EXISTS | 标明重名，保留名称输入 |
| DICTIONARY_HAS_CHILDREN | 阻止删品类，包含停用子项，不级联 |
| DICTIONARY_NOT_READY | 初始化或迁移未就绪，提供重试；不得视为空列表并恢复默认 |
| WARDROBE_CONTRACT_UNSUPPORTED | 旧/不匹配请求不能正确表达新语义，返回重新进入提示，不猜来源或静默转换 |
| WARDROBE_DETAILS_CHANGED | 明细集合已变化，保留草稿，刷新后重新核对 |
| 无权管理/访问 | 使用现有项目权限错误，后端拒绝，不能仅靠前端隐藏按钮 |

计划header `X-IW-Wardrobe-Contract: 2`仅加在衣柜业务请求。api/request.js的get/post/put当前封装不透传options，新api/wardrobe应通过专用request包装传header，或统一补充可选options且保持其他调用兼容；不能误以为给现有post添加第三个实参会生效。

仓库生产Nginx当前Access-Control-Allow-Headers没有此header，实施时须补白名单并保留既有iwtoken/Authorization/共享能力头；核实本地入口与真实生产代理。小程序原生wx.request与Web浏览器的CORS行为不能混为一次通过证明。

## 9. 迁移脚本与断言

计划交付到后端衣柜scripts下独立目录，脚本职责分离：`00-preflight.sql`、`01-schema.sql`、`02-backfill.sql`、`03-verify.sql`、恢复说明。本文不生成或执行写入SQL。

1. **预检与基线**：目标库/引擎/完整DDL、五类scope约束、完整Unicode规范化、品类搭配归类、款式谱系/父项、旧来源唯一性、标签顺序/重复、业务明细归属、记账约束定义。基线记录六业务表主键/删除标志/所属人/旧字段摘要、字典原ID/旧父子/码和其他字典摘要。不得把生产本次33/2/5固定成未来迁移断言，执行时重新获取同批快照。
2. **冻结写入边界**：覆盖衣柜业务、通用字典写入、注册模板复制、家庭初始化与涉及衣物转交的旧链路，避免回填期间产生无快照新行；其他域服务按实际依赖判断，不声称只隐藏菜单即可停写。
3. **增量结构**：新增衣柜列、独立唯一键、作用域状态、标签快照与迁移解析/批次审计。验证定义后推进阶段状态。部分DDL失败保留可诊断状态，不DROP新表伪装重跑，也不覆盖已捕获基线。
4. **来源与快照回填**：保留现有个人ID/旧码；品类谱系和搭配语义先核验再填；款式继承真实父谱系。逐业务按自身所属人+保存值建立名称基线，颜色保留原文；逻辑删除行同样处理，未设置款式不生成伪来源。家庭新树与状态同事务初始化。缺源、多候选、非规范旧token时停止并列异常，不按本地测试库策略自动翻译/补齐。
5. **迁移审计**：批次、阶段、每个标量/标签序号的raw值、owner上下文、解析方法、来源ID、名称与校验摘要均留存。当前生产那条搭配明细的1756/1767是按明细所属人解析的基线候选，2020/2031是当前衣物解析候选；二者不得互换，也不得称为证明原始选择ID。数据也可能最初由家庭可见衣物选择形成，不断言必然发生过转交。
6. **幂等**：批次基线存在时核对其完整性；已完成解析逐行比较保存结果，重复运行只核验、不按改名后的当前字典覆盖旧快照；标签按业务/类型/序号唯一且内容校验。部分批次只补未完成项，源数据摘要变化则停止，而不是继续猜测。
7. **验证**：六表原主键与删除/归属/旧值集合不变；全部适用快照覆盖；标签token数/顺序一致；父谱系/搭配语义一致；个人/家庭来源不串；记账及其他字典未变；统计按既有可见集合不漏项/放大。SQL与Java口径都需覆盖，0退出码不是完成依据。

本次生产只读会话变量异常未解决，不声称各SELECT属于已验证的一致性快照。正式预检时需在实际执行工具中证明事务控制语句生效，或在已经停写且可核验一致性的受控窗口采集基线。这里不为确定设计政策重复查询生产，也不要求凭据。

## 10. 发布与恢复顺序

微信自动更新作为主流程，不设计长期旧版双轨或独立强制升级页面。工程上采用“服务就绪后开放入口”的顺序：先完成隔离库演练及三端验收，准备已审核的新小程序版本；生产写入窗口中预检/备份/迁移/校验，部署支持快照的新后端并确认规范入口，再发布小程序并开放新功能。没有正式授权时只准备这些材料，不能实际执行。

若后端与小程序不能原子切换，短暂未就绪/旧请求返回清楚的重试或重新进入提示，不提供旧码猜测转换。新端在READY之前不能保存新自定义来源；schema已扩展但旧业务仍在写的阶段不能当迁移完成。新端可监听UpdateManager并在新版就绪、没有未保存草稿时提示适时重启；旧包不会因新增监听而被追溯升级，重新进入也不保证弱网时立即拿到新版。

恢复边界分两种：尚无新契约业务写入时，可按已校验批次备份恢复受影响数据并退回旧服务，保留审计；一旦有新来源/快照写入，优先停止相关写入并修复向前。不能直接退回只懂旧码的后端，也不能用清空标签/降级默认品类伪装兼容。确需回滚必须先确认新数据转换/备份覆盖与业务损失范围，再单独形成可审阅恢复方案。DDL不视为自动可逆。

## 11. 自验补充与证据要求

主方案AC-01至AC-19全部仍为未执行；以下补充覆盖本轮发现的技术缺口：

| 场景 | 期望与证明 |
|---|---|
| 缺省/null/空数组与Bean映射 | 仅改图片保留旧名；清空颜色/标签有效；清空必填品类拒绝；新旧来源参数冲突拒绝 |
| 保留明细/复制/重选同搭配 | 改备注不重建；copy与计划转已穿名称不变；明确重选才取新快照；伪造其他主表detailId拒绝 |
| 家庭选衣与所属人不同 | 可以按现有可见范围选择，但新增明细复制衣物真实快照；不把搭配所属人的同码当作新选择来源 |
| 初始化钩子、状态缺失和删空 | 新家庭在孩子首次读取前已有默认项；删空不补；只读成员不能触发管理写入；缺状态不是空列表 |
| 双端改名/父停用/删除与新增子项并发 | 原子失败或明确版本冲突；没有孤儿子项、跨树引用或停用项被新选 |
| 转交/退组/降角色与保存并发 | 按锁内有效归属判断，旧context被拒绝，不改变已存历史快照 |
| 部分DDL/半批回填/重跑 | 正确停在失败阶段；不重建基线、不覆盖已存名称；重跑结果与首次完整运行一致 |
| Header与网关 | 新衣柜请求实际带契约头；Nginx白名单/OPTIONS与规范入口可用，其他域头不丢；不把本地直连当生产证明 |
| AI过期候选/图片任务完成 | 过期来源保存拒绝；图片状态回调仅更新图片，不重选字典 |
| 切换期间旧包/新包与弱网 | 不产生无快照行；未保存草稿不被自动重启丢弃；提示不误清登录态 |

后端行为测试应覆盖关键不变量及隔离MySQL的约束/迁移/并发，不用只模拟Mapper成功代替数据库证明。Maven执行遵循主方案和AGENTS固定路径/仓库约定；公共iw-web变更需覆盖core/external聚合影响。小程序运行路由/语法检查及微信开发者工具目标UI；Web运行type-check/build并实看旧字典入口。后端联调服务启停只用scripts/local-backend.sh。

测试数据使用隔离库和有标记的独立测试身份，实际应用库测试账户/家庭/角色写入需在实施授权范围内落实；不得用生产数据进行行为测试。结果分别记录静态检查、数据库/接口、原生UI和生产执行，未运行的保持未执行。
