## 1. 目标与确认依据

用户原始目标：参照最近的“记账设置”，将字典管理中衣柜穿搭相关字典移到“衣柜穿搭”下，作为一个菜单项。

2026-10-21 本会话用户进一步选择：**“同时设计家庭共享字典和历史名称快照”**。因此本方案覆盖入口、五类字典、家庭权限、所有选用位置、历史展示、统计和存量迁移，不能作为单纯小程序菜单调整实施。

2026-10-21 本会话用户确认衣物选项归属：**“衣物所属人的个人选项 + 家庭共用（推荐）”**。家长代录以衣物所属人作为个人选项上下文，服务端先检查代管权限；不能改用操作人自己的个人字典。

2026-10-21 本会话用户对“新增自定义品类提供搭配归类，默认其他；例如外套归上装”的建议回复：**“是”**。因此新增品类允许选择搭配归类，默认“其他”；既有品类改名保留原搭配含义。

2026-10-22 本会话用户确认家庭字典初始化方式：**“自动填入”**，对应首次启用时自动复制系统默认五类选项。沿用该问题中说明的边界：只初始化一次，删空不自动补回，不自动公开成员的私人字典。

2026-10-22 本会话用户确认录入候选同名规则：**“合并”**，对应同类型同名项合并展示、优先衣物所属人的个人来源；旧记录已保存的来源保持不变。款式按所属品类区分；同名但搭配归类不同的品类分别展示。

2026-10-22 本会话用户确认当前衣物的名称快照边界：**“保留旧名”**，并要求**“其他问题再依次询问我”**。字典改名后，已录入衣物仍显示保存时的名称，用户明确重新选择才更新；统计按保存的名称区分新旧名称。此确认不自动覆盖复制新对象或计划状态流转的行为，后续分别询问。

2026-10-22 本会话用户确认复制旧搭配或穿着记录生成新记录的名称规则：**“保留原名”**。复制部分沿用原对象的名称快照；用户主动替换选项才使用当前名称。服务端核验原对象可复制权限，并从原对象读取真实快照。

2026-10-22 本会话用户确认穿着计划转为“已穿”时的名称规则：**“保留原名”**。仅改变穿着状态不刷新字典名称；用户主动替换选项才更新对应快照。

2026-10-22 本会话用户对“不提供款式跨品类直接移动，改为在目标品类新建后停用原款式”的建议回复：**“按照推荐来”**。该规则已确认，保留历史品类与款式关系。

2026-10-22 本会话用户对“停用品类使其子款式不可新选，恢复品类时按各款式原启停状态恢复”的建议回复：**“按照推荐处理”**。父项停用不改写子项自身状态，已有记录的名称与来源保持不变。

2026-10-22 本会话用户对“品类下还有款式时阻止删除，先删除全部子款式；停用子款式也须先删除”的建议回复：**“按照推荐处理”**。品类与款式均逻辑删除，已有业务快照保持原名，不静默级联删除。

2026-10-22 本会话用户对“以迁移时可确定的现有名称，作为老数据的名称快照”的建议回复：**“采用”**。存量品类、款式、数字标签按各记录自身所属人及保存编码唯一解析当前名称；颜色保留已有文字，迁移所得来源单独标记，不宣称恢复创建时真实名称。此后改名不回写这些快照。此确认是设计政策，不是执行数据库迁移的授权。

2026-10-22 本会话用户针对旧客户端切换问题说明：**“微信小程序都是自动升级的，应该不会出现旧版情况”**。据此采用微信正常自动更新作为主流程，不安排长期旧版兼容，也不另设衣柜强制升级页面。此回复不记为对上一条“旧版衣柜读写统一阻断”提案的直接确认。技术核实：微信官方[更新机制](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/update-mechanism.html)说明，异步更新当次仍可能使用本地旧包，发布不能立即覆盖所有现网用户；当前app.js未接wx.getUpdateManager，startVersionPolling仅轮询字典版本。短暂旧请求不能猜测转换到新来源，按新契约校验失败返回可理解的重新进入提示，属于数据完整性兜底；具体更新监听和发布顺序由实施方细化，不再要求用户选择技术更新机制。实际平台版本设置仍未核实，本轮未更改。

2026-10-22 本会话用户对“家庭共用字典采用群主、家长可维护，普通成员、儿童只读”的建议回复：**“采用”**。五类共用字典的新增、改名、启停、删除、排序及从个人添加均按该维护权限控制；可选用家庭项不等于可修改家庭字典，服务端逐次鉴权。个人字典仍由本人管理。

已确认的是上述范围、衣物选项归属、自定义品类的搭配归类、家庭模板初始化、录入候选同名规则、当前衣物保留旧名、复制旧对象保留原名、计划转已穿保留原名、款式不直接跨品类移动、品类停用恢复规则、带子款式时阻止删除品类、存量名称迁移基线及家庭共用字典维护角色。页面布局和其余工程细节为方案建议，不能冒充用户逐条确认，已按后续实施授权落实。本轮已识别的逐项产品问题已收敛；不为常规工程选择继续增加确认问题。后续若调查出现影响业务的新冲突，仍按用户要求一次询问一个问题并给推荐理由。

|---|---|---|---|

新增/改名使用底部表单：名称、必要的所属品类、原位校验、取消/保存；名称去首尾 Unicode 空白，1–32 个码点，与记账统一；不改内部空格、大小写。草稿保留原始输入，避免打断中文输入法。已确认不提供款式跨品类直接移动，使用“在目标品类新建 + 停用原项”，保留历史归属。已确认新增品类提供“搭配归类”选择，默认“其他”，例如将“外套”归为“上装”；改名时归类只读。原型已补充该字段，见 [新增品类预览](assets/category-form.png)。搭配归类沿用系统品类含义，不从用户自行维护的品类列表生成，否则会形成循环归类。

更多操作提供改名、停用/启用、删除；删除需确认并说明历史不变。排序独立进入，支持拖动和上移/下移，取消恢复基线，完成一次保存；款式只在当前品类内排序，不跨品类拖动。

首次加载、空列表、请求失败分别呈现；失败有重试。提交中防重复，写失败保留输入；写成功而刷新失败显示“已保存，列表刷新失败”，只重试读取。切换范围、所属人、家庭或登录用户时，清理旧草稿和选择，拒收迟到响应。返回未保存表单/排序时提示放弃；键盘、安全区、长名称、长列表必须在原生环境验证。

## 4. 家庭与个人规则

| 场景/角色 | 行为与确认状态 |
|---|---|
| 我的字典 | 本人管理；家庭关系变化不转移所有权 |
| 家庭共用字典 | 已确认：当前有效家庭成员使用，群主/家长可维护五类；普通成员/儿童只读；服务端鉴权覆盖全部写操作 |
| 无家庭 | 仅个人，不隐式建立家庭 |
| 衣物选择候选 | 已确认：衣物所属人的启用个人项 + 所属人当前家庭启用共用项；操作人先具备该衣物代管权限 |
| 搭配、穿着记录自身的场景/风格 | 按这条业务记录的所有者合并候选，沿用现有业务访问权限 |
| 管理别人的个人字典 | 不因可代管衣物就开放整套字典管理；必要候选只在获准的代录上下文返回 |
| 仅看自己偏好 | 只影响既有查询范围，不取消可使用家庭共用字典的资格 |
| 入组、退组、换组、解散 | 新选择按当前有效归属判定；历史快照不改，历史访问权仍遵循原业务权限 |

已确认候选列表同类型同名合并，优先所属人个人来源 ID；已保存的家庭来源不能因重新加载被同名个人来源偷偷替换。管理列表按范围独立维护，不合并成一条可编辑项。合并仅作用于有权使用且当前启用的来源：个人同名项停用而家庭项启用时，新选择使用家庭来源；两者都停用则不提供候选，不为保留个人优先而复活失效项。

款式去重键是“品类名称路径 + 款式名称”，不能把不同品类的同名款式合并。合并后的品类需保留来源集合，以便展示个人/家庭的款式并在保存时校验真实父来源；提交款式时以其真实父品类来源建立配套快照，不能提交跨树的任意 ID 组合。品类同名但系统搭配语义不同的项不自动合并，显示来源以便区分。

例如个人与家庭都有“上装”，家庭独有“上装 → 衬衫”时，合并后的上装仍展示该衬衫；用户明确新选该款式时，保存它所属的家庭品类/款式真实来源及名称快照。若两边都有同一路径“上装 → 衬衫”，则新选择优先个人的配套来源。界面合并不等于数据库合并或改写 parentId，也不允许仅刷新候选就替换旧衣物来源。

已确认家庭首次初始化复制系统模板的五类选项，一次性完成品类→款式父子 ID 映射。已有个人字典保留，不把成员私人项自动公开。初始化状态独立持久化，家庭删空后不再自动补回。初始化与状态标记在同一事务完成，并发首次访问不得重复创建；模板变更不自动覆盖已初始化家庭的自定义内容。

“从我的选项添加”生成独立家庭来源，之后双方各自维护。复制款式时自动匹配/创建同名且同搭配语义的家庭品类，重建父 ID；已存在名称含停用项均跳过并反馈，不自动启用；父项停用或语义冲突时阻止该分支复制，明确原因。只复制本人选项，不读取其他成员完整私人字典。

## 5. 名称版本、父子关系与快照

推荐沿用记账的语义：改名执行“旧项逻辑删除 + 新 ID”，记录 previous_id；启停、排序不换 ID；删除只逻辑删除；无名称变化不创建版本。已删除/替换的来源不可重新启用，ID 永不复用。

品类改名是一个事务：创建后继品类，并将当前款式关联移到新父版本、递增受影响 revision；不改款式名称及既有业务快照。保存中的旧父引用要校验版本并提示刷新，不能默默换 ID。已确认停用品类后其款式不再可供新选择，不改写款式自身启停状态；恢复父品类只恢复本来启用的子项。已确认只要品类下还有未删除的子款式，就阻止删除父品类（停用子款式也仍属于未删除子项）；先逐项逻辑删除子款式后才允许逻辑删除品类，界面说明原因，不静默级联删除。

允许删空/停用全部选项，不回填默认。品类为衣物必填时，新增衣物须有可用项，空态引导返回设置；款式、颜色、场景、风格按字段可选性处理。与字典无关的旧数据编辑仍可保存。

| 业务位置 | 要保存的来源与名称 | 何时更新 |
|---|---|---|
| 衣物 | 品类、款式、颜色来源 ID + 名称；场景/风格来源 ID 与名称数组 | 创建或用户明确重新选择该字段时 |
| 搭配自身 | 场景/风格来源与名称 | 创建或明确修改对应选项时 |
| 搭配衣物明细 | 当前已展示的衣物品类、款式来源与名称 | 新加入衣物时复制衣物快照；未替换的明细保持原样 |
| 穿着记录自身 | 场景来源与名称 | 创建或明确修改场景时 |
| 穿着记录衣物明细 | 品类、款式来源与名称 | 选衣物时复制；从搭配生成时复制搭配明细快照 |

已确认字典改名后，已有衣物保留原名称，用户明确重新选择才更新。草案进一步建议字典启停、删除、家庭关系变动也不回写上述快照。仅修改衣物图片、价格、状态、备注、所属人等非字典字段时保留既有快照；所属人变化后新增/替换选项必须按新所属人校验。调整搭配、穿着日期或天气也不能重写保留明细的名称。

已确认复制历史搭配/记录时原样保留复制部分的名称快照，用户主动替换字段才按当前候选更新；计划转已穿也保留原名，不刷新字典名称。界面建议标明不可新选的历史项。服务端对“从有权复制的原对象保留快照”和“替换选择”显式区分，仅复制服务端可证明的原对象快照，不能借此注入别人的失效来源或伪造名称。客户端名称只用于显示，最终名称由服务端生成或从原记录保留。

颜色已有 color_name 可以作为名称快照继续使用，补来源 ID；color_hex 仍为展示辅助。自定义颜色没有色值时显示名称即可，不能借本次需求增加颜色管理产品。

快照不是整条业务记录的版本审计：用户主动换分类后，衣物当前快照可以更新；已经落入搭配/穿着明细的快照继续保留。

## 6. 筛选、统计与 AI

- 历史列表、详情、日历、搭配明细直接用服务端快照，不再用查看人的当前字典解码。
- 历史筛选候选从有权查看的业务快照产生，包含停用、删除、旧名称；新增选项只来自当前有效字典，二者分开。
- 统计在现有可见业务集合内，按类型与规范化名称快照合并；款式加品类路径，禁止跨类型合并。个人/家庭同名可合并，改名前后不同名称分别统计。品类统计按衣物计数；多场景/风格按包含该标签的衣物计数，一件在同一桶内不能重复计数。
- 不借字典迁移扩大现有衣物、搭配、记录或统计可见范围。
- 当前规则搭配用固定品类码（上装=1、下装=2 等），改用来源 ID 后必须有独立的系统搭配语义映射，不能把新 ID 当旧码使用。已有品类迁移继承经预检确认的语义，改名和复制继承；已确认新增自定义品类提供“搭配归类”，默认“其他”，用户可将“外套”等归为“上装”，自动搭配按其归类处理。选项对应既有系统品类，不承诺为当前无搭配规则的归类新增组合算法。普通改名不提供搭配含义修改，避免以改名改变规则。
- AI 衣物识别与搭配推荐只接收当前上下文的可信候选，输出来源 ID，保存时再次校验权限、状态、父子关系。模型不生成字典项、不决定真实名称，不回退到停用/删空前的默认列表。图片优化只更新图片，不触碰字典快照。

## 7. 技术方案与接口边界

以下为计划新增/扩展，均非当前已有接口。数据模型见[技术契约](investigation-20261022/TECHNICAL.md)，局部更新、明细、初始化、过滤、错误、请求版本与迁移切换的补齐以[实施清单](IMPLEMENTATION.md)为准；产品语义以用户确认记录优先，尚未实施。

**存储：**复用 base_dict 的 scope_type、family_group_id、previous_id、revision，保留原字典 ID 和旧 dict_code。新业务用 source ID，不重解释原字段。为衣柜新增独立名称唯一约束（款式包含稳定品类谱系键），不能直接扩大记账生成列，破坏其现有约束。本地实查后选择新增 wardrobe_category_lineage_id、wardrobe_match_kind 与衣柜专用名称/父范围生成列、唯一键，不再另建重复scope/name/status的元数据主表；保持记账接口和既有唯一键不变。

衣物增加 category_source_id/category_name_snapshot/category_match_kind_snapshot、item_style_source_id/item_style_name_snapshot、color_source_id；color_name 保留名称值。搭配和穿着衣物明细增加相应品类/款式来源、名称及搭配语义列。多选项用 wardrobe_dictionary_tag_snapshot 表，按 business_type/business_id/dict_type/ordinal 保存 source_id 与名称，以序号唯一保留快照顺序；只允许适用组合，例如 WEAR_RECORD 只有场景。历史来源缺失允许source_id为空并在迁移解析表留存raw值/来源类型，不得成为新选项。新增个人/家庭 wardrobe_dictionary_scope_state，管理一次性初始化及scope版本。旧编码、标签字符串仅作追溯，不将 source ID 写回旧编码列。

**模块：**iw-auth 负责字典归属、家庭权限、名称版本、初始化与缓存；iw-wardrobe 负责所属人授权、选用上下文、业务快照、历史统计和 AI；通过 iw-web 中衣柜专用窄接口连接，避免 auth 与 wardrobe 模块互相依赖。可复用记账验证思想和纯名称函数，不直接把有品类树的衣柜硬塞进 BookkeepingDictionaryService.Type。

| 能力 | 计划对前端路径 | 主要契约 |
|---|---|---|
| 管理初始化 | POST /auth-service/wardrobe/dictionaries/initialize | 本人个人/有权管理的预期家庭；幂等，不补回已删空项；正常初始化在注册/家庭创建/迁移完成 |
| 管理列表/新增 | GET/POST /auth-service/wardrobe/dictionaries/items | type、scope；返回 items、canManage、scopeVersion、familyGroupId |
| 改名/启停/删除 | PUT .../items/{id}/name、PUT .../items/{id}/status、DELETE .../items/{id} | revision；改名返回 oldId、新 item |
| 排序 | PUT /auth-service/wardrobe/dictionaries/order | type、scope、parentId、完整当前集合 IDs、scopeVersion |
| 复制我的项到家庭 | POST /auth-service/wardrobe/dictionaries/copy-personal | sourceIds；返回创建、跳过及原因、父子映射 |
| 业务选项 | GET /auth-service/wardrobe/options | 衣物 ownerUserId 或已有记录上下文；先核验代管/编辑权限，再解析字典 |
| 历史筛选 | GET /auth-service/wardrobe/filters | 按已有业务可见范围生成快照名称/路径候选，不使用当前字典列表代替历史 |

计划新 Controller 的内部路径不带 /auth-service，利用现有 iw-core 兼容入口/Nginx 去前缀规则；正式实现仍需核对路由和认证。options 放 iw-wardrobe，既可使用共享衣柜字典窄接口，也能先检查实际业务权限；不能只相信 query 参数声明的 ownerUserId。

管理写入按真实 user/family 归属授权，行 revision 和集合 scopeVersion 检测并发；父子改名、复制、排序按稳定锁顺序执行，事务内再次校验家庭状态和所选来源。家庭权限查询失败禁止家庭写入，不能将失败当作“无家庭”完成越权写入。

缓存按登录会话、业务所属人、当前家庭与版本隔离；个人/家庭变更都能失效对应候选。读取用批量无锁查询，实际写入事务保留必要权限与来源锁，避免每条衣物各查一次字典。退出登录/切换家庭清空旧缓存，迟到响应不得覆盖新上下文。

迁出后通用字典类型列表、分页、detail/add/update/delete 和管理员全量同步均阻断五类管理操作；不能仅靠前端隐藏。旧 /dict/getDictListByType 与 /dict/getAllDictList 的衣柜部分不承担长期旧格式适配；迁出时保持其他业务返回契约，衣柜旧类型不再承接管理，AI和新端统一使用新接口。通用模板注册/修复不得复活用户删除的衣柜项，也不能把家庭行当 user_id=0 模板复制。

Web 本次做字典入口移除、旧 URL 阻断和提示，不另建整套 Web 衣柜设置页。若实现时发现 Web 有真实衣柜业务消费点，必须同步快照与请求兼容；本轮 src 路由/页面检索未发现衣柜业务入口，stores/dict.ts 有五类枚举。

## 8. 存量迁移与兼容策略

已按用户授权只读访问本地 iw_mixes，实测事实及SQL结果见[调查报告](investigation-20261022/REPORT.md)。本地数据不是生产当前结构或数据证明；用户已补充[生产汇总](production-readonly-20261022/RESULTS.md)，当前可唯一解析来源，未发现本地测试库中的混合标签或个人字典缺失。以下仍是未来写入迁移方案，本轮未执行DDL、回填或修复。实施需独立准备 preflight/schema/backfill/verify 脚本和恢复说明，并扩展本次只读预检为完整Unicode/权限/幂等断言；具体顺序与停止条件见[实施清单第9–10节](IMPLEMENTATION.md)。

1. 预检实际表结构、字符集、索引、字典重复名/码、孤儿款式、失效父项、业务来源与码对应关系、已删字典和旧客户端。只按原记录所属人及可证明的归属解析，禁止按当前查看人、当前家庭或同名项猜来源。
2. 先备份受影响字典和业务主键行，记录批次/行数；停止旧客户端写入或安排写入维护窗口，确保回填期间不会产生新的无快照行。
3. 增量建结构与约束；现有字典 ID 不改、不删除业务记录。为现有家庭初始化五类模板并重建款式父子映射，不替换历史个人来源。
4. 按用户已确认的“迁移时可解析名称基线”政策回填：生产现有个人字典ID与父子结构保留，品类/款式/数字标签按可证明的记录归属解析，颜色保留已保存文本并关联精确匹配来源；标注解析批次，不宣称还原创建原名。不按本地测试异常对生产补个人模板或翻译标签。1条所属人差异明细已确认双方品类/款式候选唯一且名称相同，推荐按明细自身所属人+保存码解析并记录迁移来源，衣物独立按当前所属人解析；不将所得ID冒充创建时实际保存的ID，不按衣物当前所属人覆盖历史。若实施时出现缺源、多候选或旧英文token则停止自动回填、输出异常，不能把模板或同名项伪造成历史来源。当前家庭变化不能作为历史归属证据。
5. 无法唯一还原时输出逐行异常清单并停止自动回填。颜色已有文本可保留但无来源时标记来源未知；品类/款式或标签只剩编码时不得把当前模板名称伪装成历史真实名称。已被原地改名且无审计的创建时名称无法重建；用户已确认采用迁移时可确定的现有名称，不要求额外历史名恢复。此确认不授权缺源、多候选时自行猜测或清洗。恢复能力的边界必须写入验收记录。
6. 校验业务行数、引用可追溯、父子映射、快照非空/完整、统计总量、重复计数、家庭隔离、改名后旧数据不变、删空不复活；存在歧义/权限泄漏/总量变化停止切换。
